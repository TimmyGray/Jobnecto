# Retrospective Analysis: Epic 4 - Vacancy Browsing & Filtering

Amelia (Developer): "Epic 4 story delivery is complete. This retrospective captures what worked, what needs tightening, and how we set up Epic 5."

## 1. Epic Review

### Scope Delivered

- Vacancy browsing and filtering is live for authenticated users:
  - `POST /api/v1/vacancies/filter` (browse + filter, unified route)
  - `GET /api/v1/vacancies/{id}`
- Browse mode is achieved by sending empty criteria `{}` to the filter route.
- Filter mode supports: salary range, `excludeKeywords` (title + description exclusion), skills, location, `workLocationTypes`, `categories`.
- Cursor pagination reuses the established `PagedResult<T>` envelope with `sortBy` support (`createdAt` default, `updatedAt`/`relevance`).
- Ownership semantics consistent with prior epics: cross-user reads return `404` (existence leakage prevention per Decision 7).
- Soft-delete global query filter on `Vacancy` applies across all endpoints.

### Challenges and Lessons

#### Lesson 1: Story Artifact Precision Still Drifting

Story 4.1 file header remained `Status: ready-for-dev` at retro time despite sprint-status showing `done`. This is the same finding as Epic 3 Lesson 1 — the action item was not applied.

Impact: context readers and future agents can misread implementation state.

Resolution: Story 4.1 artifact updated to `done` during this retrospective session. Deferred policy decision: full artifact discipline enforcement post-all-epics.

#### Lesson 2: Test Count Arithmetic Anomaly

Story 4.2 verified 397/397 tests. Story 4.3 verification started from 394, ending at 395. The 2-test gap is not explained in the story records.

Impact: minor confidence gap in test suite continuity.

Action (deferred): investigate and document the delta post-all-epics.

#### Lesson 3: Deferred Policy Items Carried Forward Again

Timestamp policy, validator checklist, conflict-detail privacy, and idempotency strategy from Epic 3 retro were not addressed in Epic 4.

**Deliberate decision by Timmy (Project Lead):** All policy deferred items are intentionally held until all epics are implemented. This is a scope discipline call, not an oversight. Do not carry these as open action items into Epic 5.

Dana (QA Engineer): "Noted and respected. Post-all-epics cleanup sprint it is."

#### Lesson 4: Case-Sensitivity Gap Documented But Not Fixed

`excludeKeywords` matching is case-sensitive (PostgreSQL `LIKE` behavior), but the original requirement language implied case-insensitive matching. Accepted as consistent with all other LIKE filters in the repository.

Action (deferred): system-wide case-insensitive search is a future story, not an Epic 4 fix.

## 4. Next Epic Preparation (Epic 5: Cover Letter Application Management)

Amelia (Developer): "Epic 5 is defined and ready: create, list, detail, update, and delete cover letters tied to vacancies."

### Dependency Map From Epic 4 to Epic 5

- `GET /api/v1/vacancies/{id}` (Story 4.3) — required for `vacancyId` validation in Story 5.1.
- Cover letter templates from Epic 3 — required for optional `templateId` in Story 5.1.
- Pagination envelope — reusable for Stories 5.2 list.
- Ownership semantics and soft-delete pattern — reusable across all five stories.

### Key Implementation Risks for Epic 5

- **409 Conflict for duplicate `vacancyId`:** Must be backed by a filtered unique index on `(UserId, VacancyId)` where `IsDeleted = false`. Request-level check alone does not close the race. Concurrent create integration coverage is required per Epic 5 spec.
- **`vacancyId` immutability:** PATCH endpoint must silently ignore `vacancyId` if provided. This is a deliberate product decision — needs explicit validator or handler-level enforcement (not silent EF behavior).
- **Template ID cross-ownership:** If `templateId` is provided, it must be validated as belonging to the current user. Returns `404` on mismatch (not `403`) per Decision 7.

### Significant Discovery Check

No critical discovery from Epic 4 requires rewriting Epic 5 scope. Epic 5 direction remains valid.
