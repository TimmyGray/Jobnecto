# Retrospective Analysis: Epic 3 - Cover Letter Template Library

Amelia (Developer): "Epic 3 story delivery is complete. This retrospective captures what worked, what needs tightening, and how we de-risk Epic 4."

## 1. Epic Review

### Scope Delivered

- Cover letter template CRUD is live for authenticated users:
  - `POST /api/v1/cover-letter-templates`
  - `GET /api/v1/cover-letter-templates`
  - `GET /api/v1/cover-letter-templates/{id}`
  - `PATCH /api/v1/cover-letter-templates/{id}`
  - `DELETE /api/v1/cover-letter-templates/{id}`
- Per-user uniqueness for template names is database-backed via a filtered unique index on active records.
- List endpoint supports case-insensitive name search, cursor pagination, and `contentPreview` response shaping.
- Ownership and visibility semantics are explicit and consistent with prior epics:
  - Cross-user detail read returns `404`.
  - Cross-user mutation returns `403`.
- Soft-delete behavior is preserved across list and detail paths.

### What Went Well

- Vertical-slice reuse from Epics 1 and 2 was strong; handlers, validators, and controller guardrails stayed consistent.
- Uniqueness strategy was robust: DB constraints plus conflict mapping prevented race-condition regressions.
- Testing coverage expanded across validator, handler, API, and Postgres-backed uniqueness scenarios.
- Search and pagination extensibility improved through reusable repository hooks (`Search` in `PagedQuery` and `ApplyAdditionalFilters`).

Charlie (Senior Dev): "The architectural baseline held up. We scaled a new resource family without breaking layer boundaries."

### Challenges and Lessons

#### Lesson 1: Artifact Precision Still Needs Vigilance

Story files are mostly consistent, but Story 3.5 includes a stale note saying Story 3.4 was not implemented, while sprint status and artifacts show it is complete.

Impact: context readers can misinterpret implementation state.

Action: tighten final artifact-review pass before marking stories done.

#### Lesson 2: Cross-Cutting Time Policy Is Still Unsettled

`DateTime`/`DateTimeOffset` and clock-abstraction decisions remain deferred and continue to appear in implementation notes.

Impact: this can keep producing avoidable timestamp-handling ambiguity in new epics.

Action: set project-wide timestamp policy before deeper vacancy filtering logic expands.

#### Lesson 3: Validator Cross-Field Conventions Are Still Inconsistent

Deferred notes still call out cross-field validation key naming and empty-string semantics.

Impact: API error payloads can remain technically valid but uneven for clients.

Action: define and enforce a validator checklist across all new endpoints.

#### Lesson 4: Reliability Gate Signal Is Improved

Epic 3 stories repeatedly report successful full-suite and CI-parity runs, reducing the confidence gap recorded in Epic 2 retrospective.

Dana (QA Engineer): "The reliability signal improved because Epic 3 continuously ran parity checks while implementing, not only at the end."

## 3. Technical Debt and Deferred Work Snapshot

### Carry Forward Before Production Hardening

- Timestamp policy (`DateTime` vs `DateTimeOffset`) and optional injectable clock.
- Conflict-response privacy policy for submitted identifiers.
- Validator consistency rules for cross-field and empty-string semantics.
- Idempotency strategy for retry-prone POST endpoints.

### Epic 3 Specific Deferred Items

- `CoverLetterTemplateResult` still exposes `UserId`; revisit if API privacy model tightens.
- Some Postgres test-factory robustness concerns remain deferred (low immediate risk, but monitor when more classes reuse the fixture).
