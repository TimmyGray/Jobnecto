## 2. What Went Well

### Pattern Reuse Accelerated the Epic

The Resume slice created a reusable implementation path for Education:

- MediatR command/query objects per operation.
- FluentValidation for field-level request validation.
- Mapper extensions for entity/result conversion and partial-update application.
- Controller-only auth extraction via `HttpContext.GetCurrentUserId()`.
- Handler-level ownership checks for protected resources.
- Repository-level/global-filter behavior for user scoping and soft-delete exclusion.

Winston (System Architect): "The architecture held. The team added two resource families without crossing Clean Architecture boundaries."

### Security and Ownership Semantics Were Explicit

The team distinguished read and mutation behavior clearly:

- Cross-user detail reads return `404` for no existence leakage.
- Cross-user update/delete operations return `403` where the acceptance criteria require explicit forbidden mutation behavior.
- User-owned list endpoints filter by `UserId`.
- Soft-deleted records are excluded by EF global query filters.

### Test Discipline Improved Across the Epic

The implementation logs show targeted tests, full solution tests, and Release warn-as-error gates were run during story delivery. Coverage expanded through handler unit tests and API integration tests for auth, validation, ownership, and soft-delete behavior.

Dana (QA Engineer): "The strongest quality signal is that the team kept adding endpoint-level regression tests as behavior became real."

## 3. Challenges and Lessons

### Lesson 1: Story Artifacts Need Closure Discipline

Several story files still say `Status: review` even though sprint status says those stories are `done`. Story 2.8 also contains unchecked review patch items while its completion notes say all tests passed.

Impact: future agents may misread the true state and either redo work or skip unresolved patches.

Action: close story artifacts as part of merge/post-merge documentation updates.

### Lesson 2: Cross-Cutting Time Handling Is Now Repeating

Deferred work repeatedly mentions `DateTime`/`DateTimeOffset`, cursor timestamp kind ambiguity, and direct `DateTime.UtcNow` calls in handlers.

Impact: cursor pagination and timestamp assertions remain fragile around client-provided dates and test determinism.

Action: make a project-level clock and timestamp policy decision before the pattern spreads further into Epic 3 and Epic 5.

### Lesson 3: Repository Convenience Has Ownership Trade-Offs

Detail handlers fetch by ID first, then check ownership. This preserves existing repository contracts but loads a cross-user entity before rejecting it.

Impact: behavior is correct, but ownership-aware single-record queries would reduce unnecessary reads and make the security boundary more explicit.

Action: consider an ownership-aware `GetByIdForUserAsync` pattern before implementing more user-owned resources.

### Lesson 4: Validator Edge Cases Need a Shared Checklist

Review notes surfaced repeated validator concerns:

- Cross-field rules can produce weak or empty property names.
- Empty or whitespace strings require explicit decisions.
- Some update validators permit empty strings where create validators also allow them.

Impact: API behavior can be technically valid but less helpful to clients.

Action: create a validator checklist for required/non-empty/whitespace/cross-field rules.

### Lesson 5: Deferred Work Is Valuable but Needs Triage

The deferred-work log is doing its job: it captures real risks without blocking delivery. It now needs prioritization so recurring risks do not become background noise.

Action: classify deferred work as `must-fix before Epic 3`, `must-fix before production`, or `accepted pattern`.

## 5. Technical Debt and Deferred Work

### Must Triage Before Epic 3

- Per-user template-name uniqueness must be enforced by a database constraint for Epic 3.
- Concurrent create/update integration tests are required for template-name collisions.
- Decide whether to introduce ownership-aware single-record repository access before implementing template detail/update/delete.
- Resolve validator checklist items for whitespace, max length, and cross-field error names before duplicating patterns into templates.

### Must Triage Before Production

- Cloudinary-not-configured behavior policy.
- Conflict-detail privacy policy for submitted identifiers.
- `DateTime` vs `DateTimeOffset` and cursor timestamp kind handling.
- Idempotency support for retry-prone POST endpoints.
- FK race handling between validation and persistence.
- Non-atomic `UpdateAsync` + `SaveChangesAsync` behavior after persistence failures.

### Accepted for Now

- EF global query filters remain the project-wide soft-delete enforcement mechanism.
- Direct `DateTime.UtcNow` remains consistent with current handlers until a clock abstraction decision is made.
- Generic repository + UnitOfWork remains the implementation path for Phase B resources.

## 6. Epic 3 Preparation

Epic 3: Cover Letter Template Library.

Key dependencies from Epic 2:

- Reuse Resume/Education vertical-slice structure.
- Reuse paginated list response shape: `{ totalCount, pageSize, hasNext, lastSeenId, lastSeenUpdatedAt, items }`.
- Reuse read/mutation ownership semantics:
  - GET cross-user template detail should return `404`.
  - PATCH/DELETE cross-user mutation should return `403` if the story ACs require mutation visibility.
- Reuse soft-delete filtering and `DeletedAt` behavior.

New risks in Epic 3:

- Template name uniqueness is per user and must be database-backed, not only pre-checked.
- Search by template name adds filtering behavior not present in Education.
- `contentPreview` introduces response-shaping logic and max-length preview behavior.
- Content length bounds are larger: 50-10000 characters.
